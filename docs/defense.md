# Сценарий защиты Meeting Notes

## Демонстрация

1. Запустить PostgreSQL: `docker compose up -d postgres`.
2. Экспортировать `DATABASE_DSN` из README и выполнить `go run ./cmd/meetings migrate`.
3. В первом терминале выполнить `go run ./cmd/meetings worker`.
4. Во втором: `go run ./cmd/meetings -user alice load ./testdata/meeting_release.txt`.
5. Показать напечатанные `meeting_id`, `task_id`, `status=created` и завершение команды до обработки.
6. Выполнить `status <id>` во время или после обработки; итог — `completed`.
7. Показать `get <id>`, `summary <id>`, `find "релиз"` и `chat -meeting <id> "Кто отвечает за тестирование?"`.
8. Загрузить `meeting_speech_error.txt`, дождаться `failed` и показать сохранённое сообщение ошибки. Worker продолжает обслуживать следующие задачи.
9. Создать `bob`: его `list` пуст, а `get`, `summary` и `chat -meeting` с ID Alice возвращают `meeting not found`.
10. Загрузить несколько файлов с `WORKERS=2`; объяснить и показать в JSON-логах, что пул содержит две goroutine.
11. Остановить worker через Ctrl+C: новые задачи не берутся, активные операции отменяются, задача возвращается в `created`, pool и БД закрываются.

ID не следует считать равным 1: во всех командах используется значение из `load`.

## Архитектурные ответы

### Почему CLI?

Это разрешённый основной интерфейс ТЗ. Он не требует стороннего аккаунта и отделяет короткоживущие пользовательские команды от долгоживущего worker.

### Почему PostgreSQL?

Он хранит данные и durable-очередь между процессами, обеспечивает внешние ключи, транзакции, полнотекстовый поиск и конкурентный `SKIP LOCKED`. Дополнительный брокер для масштаба учебного проекта не нужен.

### Почему пять таблиц?

`users` задаёт владельца, `meetings` хранит метаданные файла, `processing_tasks` — жизненный цикл, а `transcripts` и `summaries` имеют независимые результаты и timestamp. UNIQUE по `meeting_id` гарантирует один актуальный результат каждого вида.

### Зачем Speech и LLM интерфейсы?

Worker зависит от операций, а не от провайдера. Mock и будущий HTTP adapter взаимозаменяемы без изменения бизнес-логики. Интерфейсы небольшие и находятся на границах реальных внешних зависимостей.

### Почему mock допустим и что он делает?

ТЗ разрешает тестовые клиенты при отсутствии внешних API. Speech читает подготовленный `.txt`; LLM выполняет детерминированное извлечение. Это явно не называется настоящим AI. Реальный adapter должен реализовать тот же интерфейс и соблюдать context.

### Почему задачи в БД?

`load` завершается сразу, а `worker` запускается другим процессом. In-memory channel потерял бы задачу. Статус в БД также позволяет `status`, retry и восстановление после перезапуска.

### Как ограничен параллелизм и предотвращается двойная обработка?

Создаётся ровно `WORKERS` goroutine. Каждая делает короткую транзакцию `SELECT ... FOR UPDATE SKIP LOCKED` и меняет `created` на `processing`. Unit-тест измеряет максимальную конкурентность, integration-тест проверяет уникальность параллельных claims.

### Где транзакции?

Вместе создаются meeting и task. Вместе сохраняются transcript и `transcribed`. Вместе сохраняются summary и `completed`. Внешние вызовы не удерживают SQL-транзакцию.

### Как работает context cancellation?

Signal context передаётся в pool, затем в отдельные timeout-контексты Speech и LLM и в pgx. При отмене cleanup использует короткий независимый контекст, чтобы вернуть task в `created`.

### Как работает graceful shutdown?

После сигнала loop не захватывает новые задачи. Активные клиенты получают отмену, worker requeue-ит задачу и завершается. Main ждёт до `SHUTDOWN_TIMEOUT` и только затем закрывает pgxpool.

### Как изолированы данные?

Repository-запросы фильтруют одновременно `user_id` и `meeting_id`; проверка не откладывается до CLI. Поиск и chat также получают контекст только владельца. При этом `-user` не является защищённой аутентификацией — это честно описанное ограничение учебной модели.

### Что проверяет race detector?

Он проверяет конкурентный worker-тест, счётчики максимальной активности, очередь fake-задач, отмену и остальные unit-тесты на data race.

### Зачем в тестах используется testing/synctest?

В Go 1.25 `testing/synctest` даёт unit-тестам worker виртуальное время и `synctest.Wait()` для синхронизации. Так проверяются polling, дедлайны, лимит параллелизма, остановка и периодический recovery без реальных пауз. В этих тестах repository заменён fake-объектом; PostgreSQL проверяется отдельно настоящими интеграционными тестами.

### Какие слабые места остаются?

- нет production-аутентификации;
- mock не распознаёт произвольное аудио;
- lease восстанавливается по времени старта без heartbeat;
- нет автоматических retry/backoff для внешних API;
- нет шифрования файлов и метрик production-уровня.
